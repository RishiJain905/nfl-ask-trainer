03One optimizer step

Each step looks at 32 examples, one at a time, and adds up their gradients before changing any weight. That gives the stability of a 32-example batch with the memory of a single sequence.

1 · TokeniseChat template, thinking on (high, some low, a few off). Mask every token before the reply.
2 · ForwardFrozen Spark, bf16, its own attention. Gradient checkpointing keeps memory near 10–13 GB.
3 · LoRARank-16 adapters on q/k/v, out, gate, up, down in all 36 blocks: the only weights that learn.
4 · LossCross-entropy on the reply only (thinking + tool call + end token); logits computed only there. Optionally + λ · JEPA.
5 · BackwardGradients flow only into the LoRA weights. Accumulate.
6 · Update (after 32)Clip the gradient norm to 1.0, AdamW step, next learning rate, zero the gradients.
Every 20 steps save a full checkpoint, keep the last two Every 50 / 100 steps (pilots / real run): validation loss Every 100 / 250 steps: generate and score the held-out set; the best adapter is also kept as best/ Every step log loss, learning rate, gradient norm, tokens/s, memory to W&B

Why not 16k or 32k

The training length only has to cover the longest example, and no example in the pool is longer than 2,992 tokens (99% are under 2,024). A 16k or 32k setting would change nothing in this data. It also doesn't fit: measured at batch 1, 8,192 tokens is the ceiling on this card (14.9 GB peak, 353 tokens/s), and 10,240 tokens and above run out of memory.

Thinking traces add to every example, so the traced data sets the training length: up to 8,192 tokens fits, and anything longer gets its trace capped. Fine-tuning on short sequences leaves the base model's 1M-token context in place. Long multi-step trajectories (schema, several tool calls and results) belong to a later stage.

07The thinking-trace stage (new)

Thinking stays on, so every training reply needs real reasoning in it. The four datasets have only question and query; training on an empty <think></think> under a "think hard" system line would teach the model to skip thinking. What a pass proves, and the checker improvement

A pass means "the same results on every test database we tried": strong evidence, not proof. The example above shows the limit. Spark's LIKE '#zerowaste%' means "starts with" and the reference's LIKE '%#zerowaste%' means "contains"; on a tweet tagged #eco #zerowaste they disagree. It passed because it was checked only on random copies, whose hashtag values were exactly #zerowaste, and both queries returned the same rows.

Approved 2026-10-24, before the real run's data is exported:

  1. Catch near-misses: extra test copies whose text values sit around the queries' literals and patterns ("#eco #zerowaste", "#zerowaste!", other letter cases), so "starts with" vs "contains" and similar slips come out as different rows.
  2. Rescue the unverified: where the reference returns nothing usable, keep filling fresh copies (more seeds, more rows) until it does, up to a limit, then compare. CPU only.
  3. Re-check every answer with the new checker version: some passes become fails (near-misses), some unverified become passes or fails. The pilots' data and scores stay on the current checker, so P8 remains comparable with P1-P7.

Why temperature 1 here, and greedy for scoring

The trace run samples at Spark's own defaults (temperature 1.0, top-p 0.95). Strictness comes from the checker, not the temperature: a sloppy answer is executed, fails and is thrown away. Greedy decoding would give the same answer every time, so a second try would repeat the first one's mistake; sampling explores, and some retries succeed. Training on answers sampled at the model's natural settings is also the point of self-generated SFT. Scoring a trained adapter is the strict part: the evalset is answered greedily (temperature 0), so every pilot is judged on its single best answer.

Why two rounds

The plan gives every question up to 2 tries per thinking level. Round 0 was the first try for all 15,000 questions (27% passed: the ~3,800 examples the pilots train on). Round 1 retries only the ~11,000 question-and-level pairs that failed. It was paused after round 0 so the pilots could start ~5 hours sooner, and ran on 2026-10-24. The retries pass less often (~18% of SQL answers in its first hour, plus ~240 Cypher passes from the re-checks by 21:40), but they come from the questions the model found hard, and should add roughly half as many examples again for the real run.

Speed: ~33 answers a minute in both rounds, ~245 generated + ~400 prompt tokens a second. The 796 tokens/s in section 07 is the generation-only benchmark; a trace run also reads a ~650-token prompt for every answer and its short answers (median ~300 tokens) keep the 16 slots turning over, so prompt reading competes with generation. Worth tuning before the real trace run.

07bQuestions about this kind of SFT

Your SFTs so far were distillation runs on a given dataset (question, a larger model's reasoning, the answer), QLoRA on an H100. This plan differs from that in a few places, and these are the questions those differences raise.

1 · Does the model being trained generate answers?

No, not while it trains. Every SFT, this one included, trains by teacher forcing: the input is the prompt plus the target (here, the thought and the tool call), one forward and one backward pass, and the loss is the cross-entropy on the target's tokens only (the prompt is masked). Nothing is sampled during a training step. That part is exactly your distillation runs.

What differs is where the reasoning in the target comes from. Our four datasets have a question and a query, but no reasoning. There are three ways to get it:

So the generating happens before the SFT, in the stage that builds the dataset. The model plays the teacher and the query checker filters what it writes. Training itself is plain SFT on a fixed dataset, like your distillation runs. RL is the online version of the same idea: generate, check and update, all inside training.

Why self-generated here and not a bigger teacher: no larger model writes Spark's tool-call format and thinking style, and Spark's own traces keep its own length (kept thoughts average ~140-220 tokens) and wording. A 4B model trained to imitate a much bigger model's reasoning learns a style it can't sustain. Every kept trace is also verified by execution, and the server and checkers are the ones the RL stage will use.

2 · Why llama.cpp, and why track tokens per second?

Training doesn't use llama.cpp. It runs in PyTorch (transformers + PEFT) with the picture you know: a frozen base with a LoRA adapter trained on top. One difference from your H100 runs: there you used QLoRA, the base frozen in 4-bit to save memory. Here the 4B base fits on the 16 GB card in bf16, so it is frozen in bf16, with no quantization error in the training forward pass, and the LoRA weights (and their gradients and Adam moments) train in fp32.

llama.cpp handles the two jobs where we have to generate a lot of text, both outside the training step:

  1. Building the training data (the trace stage): 15,000 questions answered with thinking, ~5.8M generated tokens in the first round.
  2. Scoring trained adapters: 200 held-out questions answered and their queries executed, for 3 adapters per pilot across 8 pilots (~4,800 answers).

Neither job existed in your earlier SFTs: the dataset came with its traces, and training needs only forward and backward passes, so the training step's tokens per second was the only speed that mattered. That number is still tracked here (~800 tokens/s per pilot). Here, though, generation speed decides how many questions we can afford to trace and how long each evaluation takes, so it gets tracked too.

3 · How a trained adapter is scored

The adapter goes onto the frozen Q8_0 base, and llama.cpp answers the questions. For each saved adapter of a pilot:

  1. The PEFT adapter (bf16 safetensors) is converted to a GGUF LoRA (f16, ~60 MB) with the fork's convert_lora_to_gguf.py. Nothing is merged into the base.
  2. llama-server loads the shared Q8_0 base file and attaches the LoRA when it starts (--lora <file>).
  3. The 200 held-out questions (the evalset) are answered greedily (temperature 0), with thinking on high and the 1,024-token thinking budget, 16 at once: ~5 minutes.
  4. The answers' queries are executed (in WSL): SQL in SQLite on real or filled rows, Cypher in the local Neo4j on CypherBench's graphs or schema-built ones. The result is the exec accuracy: the share of checkable answers whose rows match the gold query's.

The adapter was trained against the bf16 base but is scored on Q8_0. On the smoke run's adapter this gave the same final calls as the bf16 model; every pilot is scored the same way, so the comparison is fair, and it is the setup we would deploy.

Why three adapters per pilot (steps 50, 100 and the final 107), not just the final one? The decision rule uses only the final score. Steps 50 and 100 are there for the curve. The real run's size (~52M vs ~100M tokens) depends on whether the scores are still climbing at the end of a pilot, and on this self-generated data the validation loss barely moves, so the scored curve is the only "still improving?" signal. It has already earned its place:

  • P1 went 33.2 → 34.8 → 35.0%: still rising slightly, but flattening.
  • P4 (rank 64) went 34.6 → 33.2 → 33.5%: it peaked early, the overfitting sign that ruled rank 64 out.

The cost: ~7 minutes per extra adapter (convert, start the server, answer, score), ~14 minutes a pilot, ~12% of the sweep. The step-100 point adds the least: it is only 7 steps before the end, where the cosine schedule has the learning rate near zero.

4 · How 16 answers at once fit on a 16 GB card

Memory. The weights are loaded once and shared by all 16 requests. What each answer needs for itself is only its KV cache: the attention keys and values of the tokens it has so far.

Spark's KV is small: 27 of its 36 layers use a sliding window, so they keep only each answer's last 512 tokens, and only 9 layers keep the full context (4 KV heads × 256 dims). An answer is ~1,100 tokens (prompt ~700, thought and call ~400), so 16 in flight use roughly 18k of the pool's 65k tokens. The trainer is never on the GPU at the same time: the driver stops it at each adapter snapshot for the scoring, then resumes it.

Compute: continuous batching. At every decoding step llama-server takes the next token of every active answer and runs one forward pass for all of them together. Generation is limited by reading the weights from memory: one answer alone reads all 4.4 GB per token, about 89 tokens a second. With 16 answers one read serves 16 tokens: ~800 tokens a second in total, ~50 per answer. That's about 9×, not 16×, because each answer's attention and the compute still grow; past 16 slots it measured flat (compute-bound).

"Continuous" means no answer waits for a batch to finish: when one finishes, its slot takes the next question at once, and that question's prompt is processed alongside the others' decoding, so the GPU stays busy.

Why transformers is so much slower here: its generate batches statically (sequences padded to the same length, the batch waits for its longest answer), uses eager attention and has no shared KV pool. That's ~24 tokens a second even 8 at a time on this card.

5 · Why one answer runs at ~89 tokens/s but 16 together reach ~800

A single answer is the fastest for that answer: ~89 tokens a second, against ~50 per answer when 16 run together. The ~800 is the total across all 16. Batching doesn't make any one answer faster; it gets more total work out of the GPU.

Why one answer can't go faster than ~89. To produce each token, the GPU has to read every weight of the model, all 4.4 GB of Q8_0, from its memory into its compute units. The arithmetic per weight is tiny: one multiply-add. The card streams memory at ~624 GB/s, while its compute could do far more math than that much data can feed it. One answer at 89 tokens a second reads ~390 GB/s of weights, most of what the card delivers once each answer's own attention memory and the kernel overheads are counted. The compute units sit mostly idle, waiting for weights to arrive: the limit is memory bandwidth, not compute.

Why 16 at once reach ~800 in total. In one decoding step llama.cpp reads each weight once and multiplies it against 16 token vectors, one per answer. The expensive part, reading 4.4 GB, is paid once for 16 tokens; the cheap part, the math, grows 16× and still fits in the idle compute. A 16-answer step takes only ~1.8× as long as a single-answer step, yet produces 16 tokens.

An analogy: a car versus a bus on a congested road. The car gets one person there fastest; the bus is a bit slower per trip but moves 16 people at once. The road (memory bandwidth) is the bottleneck, not the engine (compute).

Why it stops at ~16. Each answer has its own attention memory (its KV cache), which can't be shared and is read separately. Unpacking the Q8_0 weights and the math itself also start to cost real time. Around 16 answers these catch up, and more answers stop raising the total, which is why the server runs 16 slots.

The same effect shows inside a single request. The prompt is processed at ~900-950 tokens a second (the server's own logs), even for one request, because all its tokens go through the model in one pass: a batch within one request. Only the token-by-token writing of the answer is stuck at the memory-bound ~89 a second.

What to look for when you read the runs

  • Trace runs (dashboard): answers a minute and generated tokens a second (how long building the data takes), and the pass rate per dataset (how much of it is usable).
  • Pilot runs: the training loss, the training tokens a second (the familiar number), and the validation loss every 25 steps.
  • A flat validation loss is expected here: the targets are the model's own samples, which it already finds likely (P1: 0.349 at step 25, 0.347 at the end). With distillation data the loss falls a lot, because the model is learning someone else's text.
  • The signal is the scored exec accuracy on the 200 held-out questions, from llama.cpp after training at steps 50 and 100 and at the end: base model 30.6%, P1 35.0%.

10Checkpoints and crash recovery

Every 20 optimizer steps (~8–9 min of training) the trainer saves everything needed to continue as if nothing happened: the LoRA weights, the optimizer's moment estimates, the scheduler, every random-number state, the position in the shuffled data, the step and token counts, and the W&B run id. Each save is ~0.4 GB, written to a temporary folder and renamed into place, so a power cut mid-save never leaves you without a valid checkpoint. Only the newest two are kept.

After a crash, ask-trainer train --resume <run> loads the newest checkpoint, continues the same data order from the same example, and reopens the same W&B run, so the charts continue on one line. At most 20 steps are lost. The adapter is also uploaded to W&B as an artifact at every evaluation and at the end (~124 MB), so the result survives even if the PC doesn't.

Checkpoints go to F:\nfl-ask-trainer-ckpt\<run>\ (the NVMe; D: is a USB drive), ~372 MB each. Built and proven: a CPU test crashes a run, resumes it in a fresh process and gets exactly the same losses and LoRA weights as an uninterrupted run; on the GPU a smoke run was killed mid-way and resumed onto the same W&B line. Each run's adapter goes to W&B as its own artifact, ask-finetune-adapter-<run>.

15.2What trains: 31.0M numbers in 360 thin matrices

One fused attention projection

Spark computes q, k and v with a single q_k_v_proj. So one A and one B cover all three: they share one rank-16 down-projection. A model with three separate projections would get three of them (221,184 numbers instead of 139,264 for this block). It is a small difference in capacity, and the targets list names the fused matrix because that is what the module is called.

Left alone

The attention's per-head output gate g_proj (2,560 → 16), the embedding matrix (also the output head, since the weights are tied), and the RMSNorm scales. They stay frozen, and the embeddings are not saved with the adapter.

At the start A is random (PEFT's Kaiming-uniform, seeded with 42) and B is zero. That has two small consequences: the adapter adds exactly 0 until B moves, and on the first backward pass A gets a zero gradient (it is multiplied by B), so B learns first. Section 15.6 shows the gradients. In training, the 5% dropout acts on the adapter's input only; validation runs with dropout off.

Four rules keep the scores honest: a question is in one place only; the traced-and-passed questions are not also given a gold answer; the validation sets contain only questions the trainer never sees; and the datasets' own test splits are never trained on. (Source: docs/traces.md, last section.)

Seven text2cypher training questions repeated a test-split question word for word and were left out of gold. The benchmarks (BIRD dev, CypherBench's full graphs) are separate downloads in no training set.

Why this mix: what P9 showed

The traces alone are small (4,196 examples, 3.9M tokens). Pilot P9 asked whether adding the gold answers helps: P1 exactly, plus 4,235 gold examples on questions never traced. The pre-registered bar was 35.1%; it scored 41.76%, and every dataset gained. It still wrote a thought on all 200 evalset questions, at the same length.

What P9 does not settle: the proportion

P9 mixed traces and gold at about 1 : 1 by tokens (3.04M and 3.06M). The real run is 1 : 16: 3.87M trace tokens against 62.78M gold tokens, and only 3,958 thinking-on examples in 94,745 (4.2%, about 1.3 per step). P9 shows that gold helps and that thinking survives a 1 : 1 mix; whether it survives 1 : 16 is the extrapolation the run itself will answer. 15.4What is tokens/s for, if nothing is generated?

You asked: the real run does not need to generate thinking traces, does it? P9 has a speed of 815 tok/s because it was generating traces for each question?

The run generates nothing, and P9 generated nothing either. The thinking traces were written earlier, in the separate trace stage (finished 2026-10-25), and they sit in a file that the trainer reads like any other dataset. Training is teacher forcing: the reply is in the file, so it is fed in, not sampled. One forward pass over the whole sequence gives every position's prediction of its next token at once, the loss compares those predictions with the tokens that are really there, and one backward pass follows.

So the train/tokens_per_s in the log is a reading speed: the tokens in the step's 32 examples (prompt and reply, no padding, since a micro-batch is one example) divided by the wall-clock seconds of that step (32 forwards, 32 backwards, the clip and the AdamW update, with the GPU synchronised at both ends). P9 read 26,868 tokens in step 120 and took 33.1 s: 811 tokens/s.

What it is used for

  • The length of the run. 66,651,976 tokens ÷ 815 tokens/s = 81,782 s = 22.7 h (at P9's overall average of 805: 23.0 h). It is the only number that turns the data size into hours, which is why the plan quotes it.
  • A health signal. Once warm, P9 stayed between 750 and 853 on every step but one (a dip to 672 at step 174). A thermal throttle, a stuck kernel or a stall shows as a drop long before the loss moves. P9's stall at step 173 was exactly that: no step was logged any more while the trainer sat at ~320% CPU with the GPU idle.
  • A budget for changes. Rank 64, a longer max length or a larger micro-batch each move this number, so it is what to compare before paying for a change.

15.6One optimizer step, mechanically

All of this happens once per step, 2,961 times. It is the standard LoRA SFT loop. What is specific here is what is frozen, where the loss is computed, and how the memory is kept near 11 GB on a 16 GB card.

  1. One example. The next 32 examples of the shuffled order. Their token ids and label masks were computed once at start-up (94,745 examples take a few minutes), so nothing is tokenised during the run.
  2. Forward. Through 36 blocks. Each linear layer adds its adapter's output to the frozen bf16 product; the adapter path runs in fp32 (the input is cast up, the result cast back). With gradient checkpointing each block's inner tensors are dropped once the block is done.
  3. Reply states. Only the final-layer states at the positions that predict reply tokens are kept; the other ~90% of the positions never get logits.
  4. Cross-entropy. The output head is the tied embedding matrix. 1,024 positions at a time are multiplied into fp32 logits ([1,024 × 131,072] = 0.54 GB), reduced to a loss, and recomputed in the backward pass, so only one chunk of logits is ever alive.
  5. Backward. The example's loss is its summed cross-entropy divided by N, the number of scored tokens in all 32 examples of the step. Adding the 32 backward passes therefore gives the gradient of the token-mean loss of the whole step. A long reply counts for more tokens than a short one: an average trace has 206 scored tokens, a gold call 64.
  6. Clip → AdamW → scheduler → zero → log. The 360 gradient tensors are rescaled together if their joint norm is above 1.0, AdamW moves A and B, the scheduler sets the next learning rate, the gradients are cleared, and the step is written to the log.

The AdamW update, per number

g  = clipped gradient of one number θ in A or B
m  ← 0.9 · m   + 0.1   · g        running mean of g
v  ← 0.999 · v + 0.001 · g²       running mean of g²
m̂ = m / (1 − 0.9^t)    v̂ = v / (1 − 0.999^t)    t = step
θ  ← θ · (1 − lr · 0.01)  −  lr · m̂ / (√v̂ + 1e-8)

m and v are fp32 and exist for each of the 30,965,760 trained numbers: 2 × 124 MB. The weight decay (0.01) acts on θ directly, not through g; over the whole run it shrinks A and B by about 0.15%. Adam divides by the running size of the gradient, so each number moves by roughly lr per step whatever its gradient's scale. That is why the warmup exists: in the first steps v̂ rests on a handful of gradients. The clip at 1.0 rarely acts; P9's norm averaged 0.21, and its one value above 1 came on step 239, where lr was 5e-9.

How the update becomes a model

After step t, each of the 180 adapted layers is the matrix W' = W + 2 · B · A. B · A is 10,240 × 2,560 for gate_proj, the same shape as W, but it can only change W in 16 directions: its rank is at most 16.

Nothing is merged during training or scoring. For scoring, llama.cpp loads the Q8_0 base and the GGUF copy of the adapter and adds the adapter's output beside each matrix product, the same formula as in training. Folding 2·B·A into the bf16 weights is possible (the repo has merge_and_save) and is only needed to ship one self-contained model.

Where the memory goes

The weights are fixed at 8.22 GB and the adapter machinery adds 0.5 GB, so everything that varies is the ~2 GB of working memory. P9's peaks: median 10.7 GB, 90th percentile 11.3, maximum 12.6. Section 06 measured the ceiling: a single 8,192-token sequence peaks at 14.9 GB; the longest example of this run has 3,090 tokens.

The per-token figures are an estimate from the layer sizes, in bf16, counting only the main tensors (about 76,000 values per token per block; the adapters' fp32 copies come on top). The cost is one extra forward pass per block: by the usual accounting roughly a third more compute for a full fine-tune, and nearer half more here, because the frozen weights already make the backward pass cheap. It is why 815 tokens/s is below what the card does in a forward pass alone.

When something goes wrong: three ways back to the last checkpoint

  • What a checkpoint holds. The LoRA weights, AdamW's two moments, the scheduler, the Python, NumPy, torch and CUDA random states, the position in the shuffled data, the step and token counts and the W&B run id: 372 MB (355 MiB). A resume reopens the same W&B run, so the charts continue on one line. It refuses to resume if the training ids changed, so the data order is guaranteed.
  • Atomic. A save goes to a temporary folder, gets a COMPLETE marker, is renamed into place, and only then are older checkpoints deleted. A power cut at any moment leaves the previous two intact; a folder without the marker is never loaded.
  • Stall guard. The driver checks every 30 s. If neither train_log.jsonl nor events.jsonl has a new line for 15 minutes while the trainer is alive, it kills the trainer and resumes (90 minutes are allowed before the first step of each launch, for tokenising and loading). At most 6 resumes, and each must make progress. P9 stalled at step 173 with the GPU idle; the cause was the allocator's cache growing over a long run, so the cache is also released after every checkpoint.
  • Pause. Create D:\nfl-ml-data\ask\finetune\PAUSE: the trainer stops right after its next checkpoint, with nothing lost, and the driver exits. Delete the file and start the driver again to go on. A resume costs a restart (~5 min to tokenise and load) plus at most 20 steps (~9 min) of repeated work.
