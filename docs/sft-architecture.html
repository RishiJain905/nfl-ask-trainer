03One optimizer step

Each step looks at 32 examples, one at a time, and adds up their gradients before changing any weight. That gives the stability of a 32-example batch with the memory of a single sequence.

1 · TokeniseChat template, thinking off. Mask every token before the answer.
2 · ForwardFrozen Spark, bf16, its own attention. Gradient checkpointing keeps memory near 10–13 GB.
3 · LoRARank-16 adapters on q/k/v, out, gate, up, down in all 36 blocks: the only weights that learn.
4 · LossCross-entropy on the answer tokens only; logits computed only there. Optionally + λ · JEPA.
5 · BackwardGradients flow only into the LoRA weights. Accumulate.
6 · Update (after 32)Clip the gradient norm to 1.0, AdamW step, next learning rate, zero the gradients.
Every 20 steps save a full checkpoint, keep the last two Every 100 steps (pilots) / 500 (real run): evaluate Every step log loss, learning rate, gradient norm, tokens/s, memory to W&B

Why not 16k or 32k

The training length only has to cover the longest example, and no example in the pool is longer than 2,992 tokens (99% are under 2,024). A 16k or 32k setting would change nothing in this data. It also doesn't fit: measured at batch 1, 8,192 tokens is the ceiling on this card (14.9 GB peak, 353 tokens/s), and 10,240 tokens and above run out of memory.

Fine-tuning on short sequences leaves the base model's 1M-token context in place. Long multi-step trajectories (schema, several tool calls and results) belong to a later stage; that is when the length question becomes real.

09Checkpoints and crash recovery

Every 20 optimizer steps (~8–9 min of training) the trainer saves everything needed to continue as if nothing happened: the LoRA weights, the optimizer's moment estimates, the scheduler, every random-number state, the position in the shuffled data, the step and token counts, and the W&B run id. Each save is ~0.4 GB, written to a temporary folder and renamed into place, so a power cut mid-save never leaves you without a valid checkpoint. Only the newest two are kept.

After a crash, ask-trainer train --resume <run> loads the newest checkpoint, continues the same data order from the same example, and reopens the same W&B run, so the charts continue on one line. At most 20 steps are lost. The adapter is also uploaded to W&B as an artifact at every evaluation and at the end (~124 MB), so the result survives even if the PC doesn't.

Checkpoints go to F:\nfl-ask-trainer-ckpt\<run>\ (the NVMe; D: is a USB drive), ~372 MB each. Built and proven: a CPU test crashes a run, resumes it in a fresh process and gets exactly the same losses and LoRA weights as an uninterrupted run; on the GPU a smoke run was killed mid-way and resumed onto the same W&B line. Each run's adapter goes to W&B as its own artifact, ask-finetune-adapter-<run>.

12Data size: ~52M or ~100M tokens

The ~52M figure is what the four sets give with the sampling done so far, not a deliberate cap. More SQL is already on D:: SQaLe-2 has 163,468 usable examples, of which 30,000 are converted (re-converting more takes a few minutes on the CPU). Cypher is the limit: every permissively licensed Cypher set we have is already in, so a bigger mix shows text2cypher twice to keep Cypher at about a third of the tokens.

Estimates use each set's mean example length (SQaLe ~920 tokens, text2cypher ~650, gretel ~360, CypherBench ~630); the draft's tokenised count came out ~5% under its estimate (52M vs 55M), so the ~100M mix would tokenise to ~95M. Hours at the measured ~900 tokens/s. SQaLe at 60,000 means up to 7 questions per database instead of 4; gretel and CypherBench stay capped for the reasons in section 08. In pretraining, data repeated up to about four times was found nearly as useful as new data (Muennighoff et al., 2023); here the text2cypher validation loss is the check that the second pass isn't memorising. The pilots decide the size: if the validation scores are still climbing at the end of a ~4M-token pilot, more data helps and the ~100M mix is worth its extra ~14 hours; if they've flattened, the draft mix is enough. A larger mix also favours rank 64 (P4).

13Decisions for you

  1. The reply format. Today the model answers with one JSON object, {"query": "..."}, which is simple to check and to call from any code. The alternative is Spark's own tool-call format (a run_query call), which agent frameworks understand directly. Recommendation: JSON now, tool calls together with multi-step trajectories in the next stage.
  2. The pilot sweep as in section 07 (eight runs, ~11 h), including the smaller LLM-JEPA weights (λ 1 and 0.5 instead of the paper's 2).
  3. The real-run size: the draft ~52M mix (section 08) or the ~100M mix (section 12), decided by the pilots' curves unless you'd rather fix it now.
  4. The checkpoint folder F:\nfl-ask-trainer-ckpt\ (two checkpoints per run, ~0.8 GB).
  5. Benchmark downloads: SQaLe-2's populated databases, CypherBench's graphs, and BIRD / Spider dev databases. Each will be listed with its size before anything is fetched.
